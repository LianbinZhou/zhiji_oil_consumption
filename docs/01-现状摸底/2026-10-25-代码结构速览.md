## 三、界面怎么走

底部导航栏只有 **3 个 Tab**（`app_router.dart`）：

| 路由 | 页面 | 说明 |
|---|---|---|
| `/` | 首页看板 | 本月花费、总里程、平均油耗、每辆车的概览卡 |
| `/vehicles` | 车辆管理 | 增删改车辆 |
| `/settings` | 设置 | 单位、货币、主题、导出入口 |

另外两个页面**不带底部导航栏**，从车辆列表点进去：

| 路由 | 页面 |
|---|---|
| `/records/:vehicleId` | 这辆车的加油流水 |
| `/statistics/:vehicleId` | 这辆车的统计图表 |

**设计含义**：所有加油记录和统计都是"按车"隔离的，没有"全部车合并看"的入口（首页除外）。

## 四、数据怎么存

用的是 **Drift**（一个把 SQLite 包装成 Dart 对象的库，你只写 Dart 方法，它生成 SQL）。

数据库文件：`zhiji_oil.db`，存在系统"应用文档"目录。

### 两张表（`tables.dart`）

**vehicles（车辆）** — 11 个字段
`id`、品牌、型号、车牌、颜色、备注、车型、是否默认车、创建时间、更新时间

**fuel_records（加油记录）** — 13 个字段
`id`、所属车辆、日期、加油量(升)、总金额、单价、里程数、是否加满、是否亮灯、油品标号、加油站、备注、创建时间

### 一个细节

`vehicles.isDefault`（是否默认车）**是完整实现的**：`vehicles_provider.dart:149` 有 `setDefaultVehicle`（先清空全部再设目标），车辆列表里也有默认车徽章（`vehicles_screen.dart:161-181`）。

> 更正：本文初版误写"这个字段建了但代码里没人用"，是错的。实测见 `vehicles_provider.dart:149-176`。

## 五、油耗到底怎么算的（核心）

代码在 `data/models/fuel_record.dart` 第 87–93 行，整个 App 就这一个公式：

```dart
double? calculateFuelConsumption(double? previousOdometer) {
  if (previousOdometer == null || previousOdometer >= odometer) return null;
  double distance = odometer - previousOdometer;
  return (fuelAmount / distance) * 100;   // 升/100公里
}
```

**人话版**：这次加的油 ÷ 两次记录之间跑的公里数 × 100。

**但有个前提**：只有"加满油"的记录才参与计算（调用方先过滤 `isFullTank == true`），而且**至少要有 2 条加满记录**，否则算不出来。逻辑是"上次加满 → 这次加满"之间烧掉的油，才等于这次加的油量。

这就是行内说的"加满法"。

## 六、三个"名不副实"的地方（README 说了，代码没做到）

排查时发现的，写下来避免以后被误导：

### ① 亮灯法：只有字段，没有算法

README 写"支持亮灯法油耗计算"，`isLightOn`（是否亮灯）这个字段也确实从录入界面、数据库、导出里一路带着走。

但**统计、看板、油耗公式里一次都没读过它**——所有计算只看 `isFullTank`。也就是说勾不勾"亮灯"对结果毫无影响。

### ② 单位切换：只在设置页生效

设置页能选"公里/英里""升/加仑"，`settings_provider.dart` 也确实存了这些选项。

但全项目搜索 `distanceUnit` / `fuelUnit` 的使用位置，**只有 `settings_screen.dart` 自己**在用（16 处，都是下拉框显示）。首页、统计、记录页**全都没引用**。

也就是说：切成英里、加仑以后，别的页面依然显示公里和升。

### ③ 测试几乎为零

`test/widget_test.dart` 只有 1 个用例、598 字节，内容是"应用能启动、显示标题"。没有单元测试，**油耗公式没有测试覆盖**。

## 七、改代码前必须知道的 4 件事

1. **`app_database.g.dart` 是自动生成的**（1817 行）。改了 `tables.dart` 里的字段后，必须跑：
   ```
   dart run build_runner build --delete-conflicting-outputs
   ```
   手改这个文件会被下次生成覆盖。

2. **数据库有版本管理**，当前 `schemaVersion = 3`。如果加字段/改表，必须同时写迁移逻辑（`app_database.dart` 的 `migration.onUpgrade`），否则老用户升级后 App 会崩。

3. **状态管理是 Riverpod**，数据靠 `Provider.family<int>` 按 `vehicleId` 取。`databaseProvider` 定义在 `features/vehicles/providers/vehicles_provider.dart` 第 18 行——位置有点反直觉，找数据库依赖时容易找错地方。

4. **鸿蒙适配靠依赖覆盖**。`pubspec.yaml` 里用 `dependency_overrides` 把 `shared_preferences` 和 `path_provider` 指向了 atomgit 上的 OpenHarmony 分支。这意味着在普通 Flutter 环境里 `pub get` 会去拉鸿蒙仓库，网络不通时会卡住。

## 八、代码质量直观印象

| 方面 | 评价 |
|---|---|
| 注释 | 非常密集，几乎每行都有中文注释（AI 生成风格的典型特征） |
| 分层 | 清晰。数据/界面/状态三层分得开，没有把 SQL 写进界面 |
| 异常处理 | 偏"吞异常"。统计和看板里多处 `catch (e) { return null; }`，出错时界面只是空白，不报错 |
| 命名 | 一致，但同一个概念有两套模型（`FuelRecord` 是 Drift 生成的，`FuelRecordModel` 是手写的），每次都要写一遍转换函数 `_convertFuelRecord` |
| 测试 | 几乎没有 |
