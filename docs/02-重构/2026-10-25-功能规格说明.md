| 旧列 | 新列 | 说明 |

| `price_per_liter` | `unit_price` | 单价：元/升 或 元/kWh |
| `is_full_tank` | `is_full` | 加满 / 充满 |

**新增列**：

| 列 | 类型 | 说明 |
|---|---|---|
| `energy_type` | TEXT | `gasoline` / `electric`，默认 `gasoline` |
| `charge_method` | TEXT? | `fast` / `slow` / `home`，**所有充电记录都适用**（纯电全部记录 + 混动的充电记录） |

**保留列**：`id`、`vehicle_id`、`date`、`odometer`、`is_light_on`、`fuel_type`、`station_name`、`notes`、`created_at`

### 3.3 `expenses`（新表）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | 整数 | 主键 |
| `vehicle_id` | 整数 | 属于哪辆车 |
| `date` | 整数 | 时间戳 |
| **`kind`** | TEXT | **判别列（新增）**：`maintenance`（保养）/ `other`（费用） |
| `category` | TEXT | 细分类型，见下 |
| `items` | TEXT? | 仅保养：项目多选，逗号分隔 |
| `mileage` | 实数? | 仅保养：当时里程 |
| `amount` | 实数 | 金额 |
| `notes` | TEXT? | 备注 |
| `created_at` | 整数 | 时间戳 |

**为什么要有 `kind`**：UI 是保养、费用两个独立模块，Excel 分两组，统计要分开算。只靠 `category` 判"是不是保养"，会让每个使用点都写一遍白名单，改一次清单要改多处。

**`category` 取值**：

- `kind = maintenance`：机油 / 机油滤芯 / 空气滤芯 / 空调滤芯 / 火花塞 / 刹车片 / 刹车油 / 变速箱油 / 防冻液 / 轮胎 / 电瓶 / 四轮定位
- `kind = other`：保险 / 停车费 / 洗车 / 过路费 / 罚款 / **维修** / 年检 / 其他

**边界（容易混）**：

- **"维修"归 `other`**：临时修车、补胎、钣金喷漆
- **"刹车片 / 轮胎 / 电瓶"归 `maintenance`**：计划性更换
- 判断口诀：**"按里程周期该做了"算保养，"坏了才修"算费用**

### 3.4 `energy_type` 的数据契约（重要）

**`energy_records.energy_type` 是记录的"事实属性"，不是从车辆类型推导出来的。**

- 录入时按**当时的**车辆类型写入
- 用户把车辆从"油车"改成"混动"时，**不回改历史记录**
- 统计时按记录自身的 `energy_type` 分组配对

**理由**：如果按车辆类型推断，用户改一次车型，全部历史油耗数字会凭空变化，而实际烧的油没变。这是数据可信度问题。

**降级显示规则**：混动车只有加油记录、没有充电记录时，电耗显示"—"，并提示"暂无充电记录"。

## 五、能耗算法（依据审查意见重写）

### 5.1 核心公式：区间求和，不是单条

**原实现（错）**：只取本次那条记录的加油量。用户中途有一次没加满，那次的油量被丢弃，但里程照算 → 油耗被**低估**。

**正确实现**：

```dart
// 锚点 a → b：两者须为同能源类型，且满足「同一种」锚点条件（都加满，或都亮灯）
fuel = sum(quantity of records in (a, b] where energyType 相同)   // 包含中间未加满的记录
consumption = fuel / (b.odometer - a.odometer) * 100
```

- 油车：锚点 = `is_full == true` 的记录；亮灯法锚点 = `is_light_on == true`
- 电车：锚点 = `is_full == true`（充满），**只做充满法**，没有低电量法
- 混动：油、电**各自与自己同类型的锚点配对**，绝不跨类型配对

### 5.2 平均能耗：总能耗 ÷ 总里程

**原实现（错）**：`totalConsumption / count`，即各段比值的算术平均。短途（油耗高）和长途（油耗低）权重相同，结果偏大。

**正确实现**：

```dart
// 取样区间必须与 5.1 一致，锁死在「第一个锚点到最后一个锚点」之间
总里程 = 最后一个锚点.odometer - 第一个锚点.odometer
总能耗 = sum(第一个锚点到最后一个锚点之间、同能源类型的 quantity)   // 含中间未加满
averageConsumption = 总能耗 / 总里程 * 100
```

**为什么必须锁区间**：若按字面写成"所有记录的总量 ÷（max − min）里程"，分子就包含了"第一个锚点之前为了把油箱加满而加的那次油"——那部分油不是这段里程烧掉的，平均油耗会被系统性抬高。这与 5.1 要修的是同一类错误，只是搬到了聚合层。

**自洽要求**：`先分段求各段再相加` 与 `直接聚合` 两种算法必须给出同一个数。这条作为测试 9.1 的断言之一。

**统一口径**：统计页、导出 Excel、首页看板必须用同一个计算函数，不许各写一套。

### 5.3 三种车型的指标

| 车型 | 主指标 | 精度说明 |
|---|---|---|
| 油车 | 油耗 L/100km | 准 |
| 电车 | 电耗 kWh/100km | **偏高**（充电损耗，见 5.4） |
| 混动 | 油耗 + 电耗 + **每公里成本** | 前两个偏大，成本最准 |

混动统计页固定显示三个数字：

```
油耗  7.2 L/100km   （参考值）
电耗  5.8 kWh/100km （参考值）
每公里成本  ¥0.42    ← 主看这个
```

**不做"纯电模式占比"**：需要知道每段里程用什么能源，数据里没有。

### 5.4 充电损耗必须写在界面

> 电耗按充电桩计费电量计算，实际值会略低。

### 5.5 两个"每公里成本"要分开命名（避免混读）

| 指标 | 定义 | 用在哪 |
|---|---|---|
| **能耗成本/公里** | 油 + 电花费 ÷ 总里程（纯电车场景文案显示为"**每公里电费**"） | 混动/纯电统计页 |
| **用车总花费** | 油 + 电 + 保养 + 费用 | 统计页顶部"全部花费" |

## 六、单位（2026-10-25 简化：固定公制，不提供切换）

**决定：本应用固定使用 `公里(km)` / `升(L)` / `人民币(¥)`，设置页不提供单位切换。**

理由（作者原话）：面向中国用户，多一套单位只多一堆 bug 面。

| 项 | 取值 | 说明 |
|---|---|---|
| 距离 | 公里 `km` | 固定 |
| 油量 | 升 `L`；电量 `kWh` | 固定 |
| 能耗 | 油 `L/100km`；电 `kWh/100km` | 固定 |
| 货币 | 人民币 `¥` | 固定 |
| 单价 | `元/L`、`元/kWh` | 固定，不换算 |

**保留的技术约定**（防止以后有人加回切换时踩坑）：

- 存储永远用公制，任何换算只能发生在展示层
- 若将来要支持英制：油耗只允许 `gal/100mi`（越小越省），**不允许 MPG**（越大越省，方向相反会让用户看反）
- `MPG = 235.215 ÷ (L/100km)`，不是乘除 0.425144

> 代码里 `lib/shared/utils/unit_converter.dart` 保留但当前等价于恒等换算（默认公制）。设置页已移除三个选项。

## 七、数据库迁移（schemaVersion 3 → 4）

### 7.1 逐列迁移清单

| # | 操作 | 适用条件 | 失败处理 |
|---|---|---|---|
| 0 | **在打开 `AppDatabase` 之前**，文件层复制 `zhiji_oil.db` → `zhiji_oil.db.pre-v4.bak`；若存在 `-wal` / `-shm` 一并复制 | 升级前 | 复制失败则中止迁移并提示 |
| 1 | `ALTER TABLE fuel_records RENAME TO energy_records` | `from < 4` 且旧表存在 | 表不存在则跳过（已是新表） |
| 2 | `ALTER TABLE energy_records RENAME COLUMN fuel_amount TO quantity` | `from < 4` | 列已存在则跳过（幂等） |
| 3 | 同上：`total_price → amount` | `from < 4` | 同上 |
| 4 | 同上：`price_per_liter → unit_price` | `from < 4` | 同上 |
| 5 | 同上：`is_full_tank → is_full` | `from < 4` | 同上 |
| 6 | `ADD COLUMN energy_type TEXT DEFAULT 'gasoline'` | `from < 4` | 同上 |
| 7 | `ADD COLUMN charge_method TEXT`（可空） | `from < 4` | 同上 |
| 8 | `CREATE TABLE expenses (...)` | `from < 4` | 表已存在则跳过 |
| 9 | `ALTER TABLE vehicles ADD COLUMN energy_type TEXT DEFAULT 'gasoline'` | `from < 4` | 列已存在则跳过 |
| 10 | `UPDATE energy_records SET energy_type = (SELECT v.energy_type FROM vehicles v WHERE v.id = energy_records.vehicle_id)` | `from < 4` | 回填失败则保持默认值并记录 |

### 7.1b 备份为什么必须在「打开连接之前」

第二版只写"升级前复制"，没写在哪一层。如果实现成"在 `onUpgrade` 里复制"会出问题：

- 此时连接已打开、可能处于事务中
- 当前项目**未启用 WAL**（全项目 grep `journal_mode` 结果 0 处，用默认 rollback journal），所以现在复制大概率没事
- 但一旦将来有人加了 `PRAGMA journal_mode=WAL`（很常见，为并发读优化），`zhiji_oil.db` 主文件就**不含已提交的最新数据**（数据还在 `-wal` 里），备份静默变成旧快照

这种失效只有真正需要恢复的那天才被发现 = **假保险**。

**做法**：在 `main.dart` 打开数据库之前判断"旧文件存在 且 `user_version` < 4"，满足则文件层复制三件套（`.db` / `.db-wal` / `.db-shm`），然后再打开数据库。

**验收补充**：临时启用 WAL 跑一次迁移，打开 `pre-v4.bak` 后条数与迁移前一致。

**注意**：不能靠 Drift 的 `addColumn` 做改名（那是"加新列"，旧数据留在旧列里，新列全为空）。

### 7.2 必须删掉空 catch

现有实现（`app_database.dart:42-52`）：

```dart
try { await m.addColumn(...); } catch (_) {}   // ← 静默吞掉
```

**问题**：某一步失败时不报错，迁移"看似成功"，下次读库才崩 `no such column`。这正好违反"不吞异常"标准。

**要求**：失败必须记录日志 + 中止迁移 + 提示用户"升级失败，已保留备份文件"。

### 7.3 迁移测试（硬要求）

用 `NativeDatabase.memory()` 造一个 v3 schema 的库，塞 4 条加油记录 + 2 辆车，跑迁移，断言：

- 记录条数不变
- 4 个改名后的列值正确
- `energy_type` 已按车辆类型回填
- `expenses` 表存在
- 重复执行迁移不报错（幂等）

**关键特征（写实现时别记错）**：

- 记录**嵌套在车辆下面**（`vehicles[].records[]`），顶层**没有** `fuel_records`

### 8.2 新格式 V2

```json

  "schema_version": 4,
  "export_time": "...",
  "vehicles": [ { "...": "...", "is_default": false } ],

```

**命名规则（本次统一，不再混用）**：V2 的**所有键名一律 snake_case**，与数据库列名一一对应。V1 里 `vehicles`（复数小写）与 `isFullTank`（驼峰）混着来，实现时要记两套映射；V2 统一后可直接照列名读写。

**V1 → V2 键名映射表**（导入器要显式映射，别靠猜）：

| V1 键 | V2 键 |
|---|---|

| `totalPrice` | `amount` |
| `pricePerLiter` | `unit_price` |
| `isFullTank` | `is_full` |
| `isLightOn` | `is_light_on` |
| `fuelType` | `fuel_type` |
| `stationName` | `station_name` |
| `records`（嵌在车辆下） | 提到顶层 `energy_records`，补 `vehicle_id` |

**V2 相对 V1 的三处变化**：

1. 记录从车辆下**平铺到顶层** `energy_records`
2. 补齐 `is_default` 和 `settings`（"完整还原"要求）
3. `version` 升为 `"2.0"`，加 `schema_version: 4`

### 8.3 导入兼容矩阵（先写清，再写代码）

|---|---|---|---|---|

### 8.4 导入语义（本次必须拍死）

**已定：导入 = 追加到现有数据，且必须先做"导前备份"。**

理由：覆盖语义对普通用户太危险（误点就清空），而追加语义的问题是重复导入会翻倍——所以用"导前备份 + 明确提示"来兜底。

导入执行顺序（必须按此实现）：

1. 解析并校验文件格式 → 不合法直接返回错误，**不碰数据库**
2. **自动导出当前数据**到 `zhiji_oil_backup_before_import_<时间戳>.json`（导前备份）
3. 整个导入过程包在 `transaction { }` 里 → 任何一条失败则全部回滚
4. 逐条插入，累计车辆数和记录数
5. 成功后提示："导入完成：车辆 X 辆、记录 Y 条。导入前的数据已备份为 <可点击的文件名>"

**验收用例**：

- 同一份备份导入两次 → 记录条数翻倍，但第一次导入前的备份文件存在
- 备份文件里第 3 条记录字段缺失 → 导入失败，数据库记录数与导入前完全一致

### 8.5 备份落盘位置（原缺失）

**已确认（源码级，不必等真机）**：本项目实际解析到的 `path_provider_android 2.2.17` 中，`getDownloadsPath()` 调用 `getExternalFilesDirs("downloads")`，返回的是 **app-specific external storage**：

```
/storage/emulated/0/Android/data/<包名>/files/downloads
```

**不是**公共的 `/storage/emulated/0/Download`。证据：Pub 缓存内 `PathProviderPlugin.java:89-95`（`getExternalFilesDirs(...)`）、`:117-118`（`case DOWNLOADS: return "downloads"`）、`path_provider_android.dart:88-92`；`pubspec.lock` 确认版本 2.2.17。若外部存储为 null，会回退到 `getApplicationDocumentsDirectory()`（应用内部目录），离用户更远。

**仍需真机验证的只有一半**：Android 11+ 各厂商文件管理器里 `Android/data/` 是否可见（系统层受限，但部分 OEM 文件管理器仍能进）。

而这个 App 没有云端，**备份文件是唯一的数据保险**。

**已定方案：用 `file_picker` 的保存对话框（SAF）让用户自选位置。**

- 零权限（SAF 不需要存储权限）
- 用户能自己选到"下载"或网盘同步目录
- 技术旁证：`file_picker 8.3.7` 的 Android 实现中 `saveFile(...)` 走 `Intent.ACTION_CREATE_DOCUMENT`（系统文档选择器），确实不需要任何存储权限
- 验收：导出后用户能在文件管理器里找到该文件

**兜底**：若 SAF 不可用（如 Windows 桌面端），回退到 `getDownloadsDirectory()`，并在成功提示里给出**完整路径 + 可点击复制**，不能只给文件名。

## 十二、统计总览（跨车辆）· 2026-10-25 新增

**入口**：首页右上角 📊 图标 → 「统计总览」页（滚动式，不用页签）。

### 五个区块

| 区块 | 内容 |
|---|---|
| ① 总览 | 全部花费（能源/保养费用拆分）、记录里程、记录数、车辆数、平均油耗、每公里成本 |
| ② 费用构成 | 环形图 + 明细：加油 / 充电 / 保养 / 其他费用，带占比 |
| ③ 年度报告 | 每年的花费、里程、能耗 + 进度条 + 与上一年同比 |
| ④ 车辆对比 | 每辆车的里程、总花费、每公里成本、平均能耗；按每公里成本从低到高排，标"最省/最费" |
| ⑤ 里程统计 | 近 12 个月里程条 + 说明 |

### 里程口径（作者 2026-10-25 定）

> 只统计用户实际录入的里程：**每辆车「最大里程 − 最小里程」，各车相加**。
> 中途漏记不特殊处理（缺口天然被首末差值覆盖）。

| 情形 | 处理 |
|---|---|
| 某车记录 < 2 条 | 该车里程算 0，界面上标「里程不足」，不参与排行 |
| 某月记录 < 2 条 | 该月里程显示「—」，图上不画柱（不代表没开车，只是算不出来） |
| 表显里程（最新一条原值） | **不参与任何统计**，只在车辆卡片显示 |
| 混动车加油+充电 | 里程按里程表去重，只算一次（不因两种能源重复累加） |

### 数据来源

全部来自现有 `energy_records` + `expenses`，**没有新增采集、没有新增权限**。
