### ① "getDownloadsDirectory 返回私有目录"被当成结论——批评部分成立，但结论本身是对的，而且现在有源码级证据

**接受批评的部分**：我上一轮在问题描述里写"原因是：`path_provider` 在 Android 上给的是应用私有目录"，同时又把它列进"推测"小节——**同一份报告里既当结论又当推测，是我自己的报告纪律没守住**（违反我自己列的第 3、4 条铁律）。DSH 把它降级为"推测，需真机验证"并补验证方法，这个处理是对的。

`getExternalFilesDirs("downloads")` 返回的是 **app-specific external storage**，即
`/storage/emulated/0/Android/data/<包名>/files/downloads`，**不是**公共的 `/storage/emulated/0/Download`。
（`pubspec.lock:564-571` 确认实际解析到的就是 `path_provider_android 2.2.17`。）

- **已确认（源码级）**：`getDownloadsDirectory()` 在本项目实际使用的 `path_provider_android 2.2.17` 上返回
  `Android/data/<包名>/files/downloads`（证据：上面 3 处文件行号），是应用专属目录，不是用户意义上的"下载"目录。
  若外部存储为 null，代码会回退到 `getApplicationDocumentsDirectory()`（应用内部目录），离用户更远。
- **仍需真机验证（只有这一半）**：在 Android 11+ 的**各厂商**文件管理器里，`Android/data/` 是否可见

结论不变：**规格里"改用 SAF 保存对话框"的方案是对的**，而且我给了一条旁证——`file_picker 8.3.7` 的 Android 实现确实走系统文档选择器，零权限：

## 三、本轮新增问题

### [N1] 单位换算表里 MPG 的系数错 100 倍（Major · 硬错）

- **位置**：`docs/02-重构/2026-10-25-功能规格说明.md` §6 换算表第 3 行
- **证据**：表中写 `L/100km → MPG：÷ 0.425144`。以 8 L/100km 核算：
  ```
  真实 MPG           = 235.214583 / 8      = 29.40
  真实 gal/100mi     = 8 × 0.425144        = 3.40
  自洽校验           = 100 / 3.40          = 29.40   ← 与真实 MPG 一致
  表里的算法         = 8 / 0.425144        = 0.29    ← 差 100 倍
  ```
- **原因**：`0.425144` 是 L/100km → gal/100mi 的系数（正确），而 `1/0.425144 = 2.352` 是"1 个 L/100km 对应多少……"的量纲只剩每加仑英里数的百分之一；正确系数应为 **MPG = 235.215 / (L/100km)**（等价于 × 2.35215 后再 ×100）。
- **影响**：本版已决定"不用 MPG"，所以**当前不产生 bug**——但换算表是给实现者照抄的，这一行会作为"已知公式"留在文档里。将来任何一次"顺手支持 MPG"（很可能是英文 README 或外国用户提 issue 时）都会直接踩上，且错得很隐蔽（数字偏小 100 倍，用户会以为车极费油）。
- **建议**：改成 `L/100km → MPG（美制）：235.215 ÷ 值`，或直接删掉这一行、只留 `gal/100mi`，并保留那句"不用 MPG"的方向说明。顺手核对同表另外 4 行（km/mi、L/gal、gal/100mi、kWh/100mi 均核算正确）。

### [N2] 加权平均的"总能耗"与"总里程"取样区间没锁死，仍会引入偏差（Major）

- **位置**：规格 §5.2 的两行公式；对照 §5.1
- **证据**：
  ```
  §5.2  averageConsumption = 总能耗 / 总里程 * 100
        其中总里程 = max(odometer) - min(odometer)（不含首条记录之前的里程）
  §5.1  fuel = sum(quantity of records in (a, b] ...)      ← 明确是"锚点区间"
  ```
- **原因**：§5.1 把"区间求和"讲清了，§5.2 又退回成"总能耗 / 总里程"，但**没有说明"总能耗"是不是也按锚点区间取**。
- **影响**：若实现者按字面写 `sum(所有记录 quantity)`：
  - 分子包含了"第一条锚点之前为了把油箱加满而加的那次油"（这部分油不是这段里程烧掉的）；
  - 分母却是 `max - min` 的里程；
  - 于是平均油耗被系统性抬高，且抬高的幅度取决于"第一条记录到第一个加满锚点之间加了多少油"。
  这正好是 §5.1 想修掉的同一类错误，只是搬到了聚合层面。电车/混动的"总电量 ÷ 总里程"同理。
- **建议**：§5.2 补一句锁死取样口径：
  ```
  总里程 = 最后一个锚点.odometer − 第一个锚点.odometer
  总能耗 = sum(第一个锚点到最后一个锚点之间、同能源类型的 quantity)   // 含中间未加满
  ```
  并注明"两种计算方法（先分段再相加、直接聚合）必须给出同一个数"，作为测试 9.1 的一条断言。

### [N3] "迁移前复制数据库文件"没说在哪一层复制，按 WAL/journal 有取到旧快照的风险（Major · 实现注意）

- **位置**：规格 §7.1 步骤 0；重构目标 4.3
- **证据**：
  ```
  规格 §7.1  step 0  复制数据库文件为 zhiji_oil.db.pre-v4.bak | 升级前 | 复制失败则中止
  代码现状：lib/data/database/app_database.dart:365  return NativeDatabase(file);
            全项目 grep journal_mode / WAL → 0 处（未启用 WAL，默认 rollback journal）
  ```
- **原因**：文档只写"升级前复制"，没写"在数据库连接打开之前、文件层面复制"。若实现成"在 `onUpgrade` 里复制"，此时连接已打开、可能处于事务中；一旦将来有人加了 `PRAGMA journal_mode=WAL`（很常见，为并发读优化），`zhiji_oil.db` 主文件就可能**不含已提交的最新数据**（数据还在 `-wal` 里），备份静默失效——而这种失效只有在真正需要恢复的那天才被发现。
- **影响**：备份文件存在、提示"已保留备份"，但内容是旧快照 → 数据保险变成假保险。这是本项目唯一"不可挽回"的事故类型。
- **建议**：
  1. 复制动作放在"打开 `AppDatabase` 之前"（用文件存在性 + 一次只读连接读 `PRAGMA user_version` 判断版本，或干脆在 `main.dart` 打开库前按"是否存在旧版文件 + 版本号 < 4"决定是否复制）；
  2. 复制时**三件套一起**：`zhiji_oil.db`、`zhiji_oil.db-wal`、`zhiji_oil.db-shm`（后两个不存在就跳过）；
  3. 验收补一条：临时启用 WAL 跑一次迁移，`pre-v4.bak` 打开后条数与迁移前一致。

### [N4] 录入校验这一项在第二版清单里消失了（Major · 承诺回退）

- **位置**：`重构目标 v2`（通篇无此项）、`功能规格 v3 §4`（只有排序键，无校验规则）；对照 `03-参考/…小熊油耗拆解.md §九` 与第一版重构目标 1.3
