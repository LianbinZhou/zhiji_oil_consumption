## 二、Blocker

### [B1] 编辑混动车的充电记录 → 记录被改写成加油记录（数据静默损坏）

- **位置**：`lib/features/records/presentation/record_dialog.dart:46`、`:53`、`:94-110`、`:262-302`
- **证据**：
  ```dart
  46:   String _recordEnergyType = 'gasoline';
  53:   bool get _isElectricMode => _recordEnergyType == 'electric';

  94:  Future<void> _loadVehicleEnergyType() async {
        ...
  104:      _recordEnergyType =
  105:          v.energyType == 'electric' ? 'electric' : 'gasoline';   // 只看车辆类型

  initState:  if (widget.record != null) { ...按 record 回填 amount/odometer/isFull… }
              // ← 通篇没有 _recordEnergyType = widget.record!.energyType;
              // ← 也没有 _selectedChargeMethod = widget.record!.chargeMethod;
  ```
- **原因**：编辑态从不读"这条记录自己的 `energyType`"，而是用"车辆类型推出来的默认值"覆盖它。混动车的默认值是 `gasoline`（`hybrid → gasoline`，见 `:104-105` 与注释"混动默认按油"）。
- **影响**（混动车主，两步即可触发）：
  1. 录一条充电记录（energyType=`electric`，含 kWh、充电方式）；
  2. 点开这条记录再点保存 → `updateRecord(energyType: 'gasoline', chargeMethod: null)`。
  结果：这条记录变成"加油记录"，`quantity` 里的 kWh 被当成升、`unit_price` 里的元/kWh 被当成元/升并入油耗统计；充电方式被清空。**用户看到的只是"数字变了"，没有任何提示**。混动正是本版新加的主打能力。
- **建议**：
  ```dart
  // initState 里，编辑态优先用记录自身的事实属性
  if (widget.record != null) {
    _recordEnergyType = widget.record!.energyType;   // 不从车辆推导
    _selectedChargeMethod = ...;                     // 见 B1 附带问题
  }
  ```
  并让 `_loadVehicleEnergyType()` 只在新记录时决定默认值（`if (widget.record == null)`）。
- **附带（同一处，一并修）**：`_selectedChargeMethod` 编辑态未回填 → 即使 `energyType` 修好，编辑一次充电记录仍会丢掉"快充/慢充/家充"。参考 `initState` 里 `_selectedFuelType = widget.record!.fuelType` 的写法补一行。注意 `_chargeMethods` 是中文标签（`['快充','慢充','家充']`），而库里存的是 `fast/slow/home`，需要一次映射（现有代码保存时怎么把中文转成 `fast`，也要确认，见 Nit n5）。

### [B2] 「清理所有数据」不删 `expenses`

- **位置**：`lib/features/settings/presentation/settings_screen.dart:317-330`；对照 `app_database.dart:455-459`
- **证据**：
  ```dart
  317: Future<void> _clearAllData(BuildContext context) async {
  322:   await database.deleteAllEnergyRecords();
  325:   await database.deleteAllVehicles();
         // ← 没有 deleteAllExpenses()
  329:   SnackBar(content: Text('所有数据已清理'))

  455: Future<int> deleteAllEnergyRecords() => delete(energyRecords).go();
  457: Future<int> deleteAllExpenses() => delete(expenses).go();      // ← 写好了，没人调用
  459: Future<int> deleteAllVehicles() => delete(vehicles).go();
  ```
- **影响**：
  - 用户点了"确认删除"、看到"所有数据已清理"，**保养与费用记录仍完整留在数据库文件里**（车辆被删后成了孤儿行，`vehicle_id` 指向不存在的 id）；
  - 这条路径也是"我要换手机/清空重来"的主要入口，残留数据既违背界面承诺，也违背 PRIVACY.md 里"你的数据只在你手机上，你说了算"的口径；

- **建议**：`_clearAllData` 补 `await database.deleteAllExpenses();`，并且按 `expenses → energy → vehicles` 的顺序放进一个 `transaction`；验收补一条"清理后用 DB 工具查三张表行数均为 0"。

## 三、Major

### [M1] 首页看板仍用旧算法，与统计页对同一指标给出两个数字

- **位置**：`lib/features/dashboard/providers/dashboard_provider.dart:127-152`（总览）、`:204-210`（单车主卡片）
- **证据**：
  ```dart
  127:  final fullTankRecords = sortedRecords.where((r) => r.isFullTank).toList();
  135:    final consumption = current.calculateFuelConsumption(previous.odometer);  // ← 旧公式：单条油量 ÷ 里程差
  151:  averageFuelConsumption = fuelConsumptions.reduce((a,b)=>a+b) / fuelConsumptions.length;  // ← 旧口径：算术平均

  204:  final fullTankRecords = sortedRecords.where((r) => r.isFullTank).toList();
  206:    recentFuelConsumption = fullTankRecords[0].calculateFuelConsumption(fullTankRecords[1].odometer);
  ```
  `calculateFuelConsumption` 本体仍是旧实现（`lib/data/models/fuel_record.dart:110-118`：`(fuelAmount / distance) * 100`）。
- **原因**：本次只把**统计层**换成了 `weightedConsumption`，首页两条路径没跟着换；项 3（模型合并）未做，于是旧手写模型还活着，旧公式就还有调用方。
- **影响**：首页"平均油耗"依然**漏算未加满的油量 + 用算术平均**。举例（就是你们自己定的验收用例）：加满 40L → 未加满 20L → 加满 15L，里程差 500 km：
  - 统计页（新）：`(20+15)/500×100 = 7.0`；
  - 首页（旧）：只看两条加满记录 → `15/500×100 = 3.0`。
  同一个 App，首页 3.0、统计页 7.0。用户第一反应是"数据不准"，正好否掉本次重构最大的卖点。这与进度表 `2.3 算法统一 ✅ 已完成`、规格 §5.2"统计页、Excel、首页看板必须用同一个计算函数"直接冲突。
- **建议**：把 `dashboard_provider` 改为读 `weightedConsumption`（同一函数、同一 `energyType` 过滤），删掉 `_convertFuelRecord` / `_convertVehicle`；补一条测试或至少一条"首页数字 == 统计页数字"的人工验收。**这条建议在 v1.0.0 发布前修，否则发布说明里的"算法修正"名不副实。**

### [M4] 亮灯法是"加满优先、不足才退亮灯"，且界面上没有算法标注

- **位置**：`lib/features/statistics/providers/statistics_provider.dart:206-207`；`lib/features/statistics/presentation/statistics_screen.dart`（全文无"加满法/亮灯法"字样）
- **证据**：
  ```dart
  // 加权平均油耗（先加满法，数据不够再退亮灯法）
  double? avgConsumption = weightedConsumption(fuel, useLightAnchor: false);
  avgConsumption ??= weightedConsumption(fuel, useLightAnchor: true);
  ```
  ```
  $ grep -rn "亮灯法\|加满法\|算法" lib/features/statistics/presentation/  → 0 处
  ```
- **原因**：规格 1.2 的动作是"锚点可以是加满或亮灯，**勾哪个用哪个**"+"统计页注明当前算法"；实现成了"全局先试加满，不够再试亮灯"，且不告诉用户现在用的是哪种。
- **影响**：
  - 用户有 ≥2 条加满记录时，他勾的"亮灯"**完全不起作用**——README 第 95 行却写"勾『油灯亮』时改用灯亮作为锚点"，属行为与文档不符；
  - 用亮灯法的用户看到的数字**没有标注来源**，无法判断该信哪个；
  - 验收表 1.2 的验收方法（"2 条亮灯记录对比"）在这种实现下无法判定通过——如果那两条记录同时也勾了"加满"（对话框里"加满"默认是 `true`，见 `record_dialog.dart:37` 附近 `_isFullTank = true`），结果会与加满法**完全相同**，验收必然误判。
- **建议**：三选一并在文档里写清：(a) 按"用户本次勾了哪个"逐条决定锚点；(b) 保留 fallback，但在统计页加一行小字"当前按加满法计算 / 按亮灯法计算"，并把 README 改成"数据不足时自动退回亮灯法"；(c) 暂时下架亮灯法描述。**最低成本是 (b)**。
