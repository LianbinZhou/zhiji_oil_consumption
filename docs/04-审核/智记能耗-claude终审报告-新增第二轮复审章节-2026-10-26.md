## 二、🔴 P0 阻断级缺陷（4 项）

### P0-1　「记一次保养 / 记一笔费用」100% 保存失败（v1.1.2 新引入的回归）

**位置**

- `lib/features/expenses/providers/expenses_provider.dart:40-62`（`addExpense`）
- `lib/features/expenses/presentation/expense_dialog.dart:225-236`（调用点）
- `lib/data/database/app_database.g.dart:1447-1449`、`:1518-1523`（Drift 生成的必填校验）

**问题**

`addExpense` 构造 `ExpensesCompanion` 时**漏掉了 `createdAt`**：

```dart
await db.insertExpense(ExpensesCompanion(
  vehicleId: ...,
  date: ...,
  kind: ...,
  category: ...,
  items: ...,
  mileage: ...,
  amount: ...,
  notes: drift.Value(notes),
  // 编辑不该改创建时间（不传 createdAt，交给 write 保持原值）   ← 这行注释放错了方法
));
```

而 `expenses.created_at` 是 **NOT NULL 且无默认值**，Drift 生成代码里是：

```dart
late final GeneratedColumn<int> createdAt = GeneratedColumn<int>(
    'created_at', aliasedName, false,
    type: DriftSqlType.int, requiredDuringInsert: true);   // app_database.g.dart:1447-1449
```

插入时 Drift 会调用 `validateIntegrity(isInserting: true)`，命中 `context.missing(_createdAtMeta)`（`:1521-1522`），直接抛 `InvalidDataException`，SQL 根本不会执行。

**历史证据（这条不是猜测）**

```text
commit e2c961a  fix: v1.1.2 修复优惠金额未落库等 4 个问题（第四轮复审）
@@ -57,7 +57,7 @@ class ExpensesNotifier
       notes: drift.Value(notes),
-      createdAt: drift.Value(DateTime.now().millisecondsSinceEpoch),
+      // 编辑不该改创建时间（不传 createdAt，交给 write 保持原值）
     ));
```

上一轮想修的是 **`updateExpense` 覆盖 `created_at`（m2）**，结果删到了 **`addExpense`** 头上。这个 commit 就是当前 `1.1.2+13` 的发版提交。

**用户看到的现象**

> 添加保养/费用 → 点「添加」→ 弹 `保存失败：InvalidDataException: Unable to validate inserted data ... expenses.created_at is missing ...`

**影响**：保养、费用两大功能完全不可用；且 `expenseTotalCost`、统计总览的「保养/费用」永远是 0。

**修复**

```dart
await db.insertExpense(ExpensesCompanion(
  ...
  notes: drift.Value(notes),
  createdAt: drift.Value(DateTime.now().millisecondsSinceEpoch), // ← 补回来
));
```

同时把 `updateExpense` 里的 `createdAt` 去掉（`expenses_provider.dart:86`），那才是 m2 该修的地方。

> **这也说明测试覆盖有洞**：`test/` 下有三类测试，但**没有任何一条覆盖 `expenses` 的增删改**（`record_write_test.dart` 只测 `energy_records`）。真机「完整流程验收通过」的说法与这条缺陷直接矛盾，说明支出功能要么没测，要么测的是旧包。

### P0-2　点「设为默认」会把车辆能源类型静默重置为「油车」

**位置**

- `lib/features/vehicles/providers/vehicles_provider.dart:150-188`（`setDefaultVehicle`）
- `lib/data/database/app_database.dart:186-188`（`updateVehicle` 使用 `replace`）
- `lib/data/database/app_database.g.dart:75-79`（`energy_type` 的 `defaultValue`）
- Drift 源码 `update.dart:146-150`（`replace` 会为缺失列补默认值）

**问题链路**

1. `setDefaultVehicle` 在更新车辆时构造的 `VehiclesCompanion` **没有 `energyType`**：

```dart
await database.updateVehicle(VehiclesCompanion(
  id: drift.Value(vehicleId),
  isDefault: const drift.Value(true),
  brand: ..., model: ..., licensePlate: ..., color: ..., notes: ...,
  vehicleType: ...,
  createdAt: ..., updatedAt: ...,
  // 没有 energyType
));
```

2. `updateVehicle` 用的是 `.replace()`：

```dart
Future<bool> updateVehicle(VehiclesCompanion vehicle) {
  return update(vehicles).replace(vehicle);
}
```

3. Drift 的 `replace` 语义是 `INSERT OR REPLACE`，并且明确会对缺席列**补默认值**：

```dart
// drift/lib/src/runtime/query_builder/statements/update.dart:146-150
for (final column in table.$columns) {
  if (column.defaultValue != null && !_updatedFields.containsKey(column.$name)) {
    _updatedFields[column.$name] = column.defaultValue!;
  }
}
```

4. `energy_type` 的默认值正是 `gasoline`：

```dart
late final GeneratedColumn<String> energyType = GeneratedColumn<String>(
    'energy_type', aliasedName, false,
    requiredDuringInsert: false,
    defaultValue: const Constant(EnergyTypes.gasoline));   // :75-79
```

**结果**：用户对一辆纯电车（或混动车）点「设为默认」，它的 `energy_type` 会被改成 `gasoline`。原默认车如果在第一轮循环里被更新，同样被改成 `gasoline`。

**为什么这是 P0**：这是**静默的数据损坏**，没有任何报错、没有确认框。后果连锁：

- 车辆卡片上的「纯电/混动」徽标消失；
- 进入该车录入时，表单从「充电」变回「加油」；
- 统计页开始显示「平均油耗 / 油价范围」，电耗消失；
- 混动车失去加油/充电切换开关。

历史记录本身的 `energy_type` 不会变，所以统计还能算出电耗，但车辆维度的展示与录入全乱了。用户几乎不可能自己定位原因。

**修复**：`updateVehicle` 改用 `update(vehicles)..where((t) => t.id.equals(id))).write(companion)`（与 `updateEnergyRecord` 一致的语义），或在 `setDefaultVehicle` 里补齐 `energyType`。**两者建议都做**——前者的语义正确性更重要，否则下一个新增列还会踩同一个坑。

### P0-4　导入没有大小上限，100MB 文件必然 OOM

**位置**：`lib/features/export/providers/export_provider.dart:307-333`

```dart
final picked = await FilePicker.platform.pickFiles(
  type: FileType.custom,
  allowedExtensions: ['json'],
  allowMultiple: false,
);
...
final content = await File(filePath).readAsString();   // ← 整个文件读进内存
final decoded = jsonDecode(content);                    // ← 在 UI isolate 上构建完整对象树
```

**问题**

- 没有任何大小检查（`picked.files.single.size` 就在手边，完全没用）；
- `readAsString` 会把文件转成 UTF-16 字符串（体积约 ×2）；
- `jsonDecode` 再构建一棵完整的 `Map/List` 树（通常 ×5～×10）；
- 全程跑在 **UI isolate**，期间界面卡死。

一个 100MB 的 JSON（恶意或误选），内存峰值轻松到 1GB 以上。Android 上直接 `OutOfMemoryError`，进程被杀，**用户以为数据丢了**（实际库没坏，但体验等同于崩溃）。中低端机上 20～30MB 就可能触发。

**修复**（按成本从低到高）

1. 读取前校验 `size`，超过阈值（建议 10～20MB）直接拒绝并提示；
2. 把 `readAsString + jsonDecode` 放进 `compute()` / `Isolate.run()`；
3. 更彻底：流式解析，逐条 `insert`。

## 三、🟠 P1 严重隐患

### P1-1　导入与手工输入的数值完全没有边界校验 → 脏数据落库，统计页崩溃

**入口**：`export_provider.dart:624-637`

```dart
double _toDouble(dynamic v) {
  if (v is num) return v.toDouble();
  if (v is String) return double.tryParse(v) ?? 0;   // "NaN" -> NaN, "1e999" -> Infinity
  return 0;
}

int _parseMs(dynamic v) {
  if (v is num) return v.toInt();                    // 任意大整数都收
  if (v is String) { ... }
  return DateTime.now().millisecondsSinceEpoch;      // 解析失败 -> 悄悄改成"现在"
}
```

**问题与后果**

| 脏值 | 落库后炸在哪 |
|---|---|
| `date` 超出 Dart 时间范围（±8.64e15 ms） | `DateTime.fromMillisecondsSinceEpoch` 抛 `ArgumentError`：`app_database.dart:388`、`dashboard_provider.dart:45/53`、`statistics_provider.dart:254/271/341`、`overview_stats_provider.dart:262/269/320/327`、`records_provider.dart:20/32`、`export_provider.dart:73/84/188/229...` |
| `amount`/`quantity` 为 `NaN` 或 `Infinity` | `statistics_screen.dart:981` 的 `value.toInt()` → **`UnsupportedError`**（非有限数不能转 int），在 `build()` 里抛出 → 灰屏/红屏 |
| 同上 | **导出 JSON 也会挂**：`export_provider.dart:128` 的 `JsonEncoder` 不支持 NaN/Infinity，抛 `JsonUnsupportedObjectError` |
| 同上 | Excel 导出 `DoubleCellValue(Infinity)` → `exportToExcel` 无 try-catch（见 P1-7） |

注意：**不只是导入**。`record_dialog` / `expense_dialog` 的校验器只判断 `double.tryParse(value) != null`，而 Dart 的 `double.tryParse('NaN')` 和 `double.tryParse('Infinity')` **都返回非 null**。数字键盘打不出字母，但粘贴可以。所以正常 UI 也能写入 NaN。

另外，`_parseMs` 遇到非法日期时**静默替换为当前时间**，这是更隐蔽的数据污染：用户导入一个字段拼错的备份，历史记录会被改成「今天」，且无任何提示。

**建议**：在 `_toDouble` / `_parseMs` 里做白名单式校验（`isFinite`、`0 <= value <= 1e9`、日期范围 2000–2100），非法值**拒绝导入并报告行号**，而不是静默兜底。

### P1-3　「恢复数据」实际是「追加数据」，重复导入会产生重复车辆与重复记录

**位置**：`export_provider.dart:353-362`、`469-486`；提示文案 `settings_screen.dart:377-379`

导入时只做了 `clearAllDefaultVehicles()`，然后**直接 `insertVehicle` 拿新 id**，既不删旧数据，也不做任何去重：

### P1-5　`targetSdk = 34` 无法通过 Google Play 审核

**位置**：`android/app/build.gradle.kts:32`（`targetSdk = 34`），`README.md:54` 还专门解释了「为什么锁 34」。

自 **2025-08-31** 起，Google Play 要求新应用和更新必须 target **API 35**。今天是 2026-10，`targetSdk=34` 的包会被 Play Console 直接拒收。

**注意**：如果你们的发布渠道只有 GitHub Releases（按 README 的描述确实是），这不是问题；但用户的要求里明确提到「上架 App Store / Google Play」，那就必须先升到 35（并处理 edge-to-edge 强制、`compileSdk` 已是 36，改动面可控）。

### P1-6　导出全链路缺少 try-catch，失败时用户只看到「正在导出…」

**位置**

- `settings_screen.dart:350-368`（`_exportJson`）、`:477-495`（`_exportExcel`）
- `export_provider.dart:48-139`（`exportToJson`）、`154-270`（`exportToExcel`）

`_saveBytes` 内部有 try-catch，但**数据读取、JSON 编码、Excel 编码都在 `_saveBytes` 之外**。只要 `jsonEncode` 抛 `JsonUnsupportedObjectError`（见 P1-1）或 Excel 编码失败，异常会一路冒泡成未捕获的异步错误：

- 进度 SnackBar 永远停在「正在导出 Excel...」；
- 用户没有任何失败提示，会反复点。

**修复**：把 `exportToJson` / `exportToExcel` 整体包进 try-catch，返回 `ExportResult(success: false, message: ...)`。

### P1-7　「实付金额」会被自动计算静默覆盖

**位置**：`record_dialog.dart:169-180`、`:433`、`:457`、`:481`

数量、单价、优惠三个框的 `onChanged` 都调用 `_calculatePrice()`，而它**无条件覆写** `_totalPriceController.text`。

用户的手动流程经常是：先填数量 → 填单价（金额自动算出）→ **手动改金额**（实际付款和理论值不一致，这很常见）→ 回头修一下单价 → **手动改的金额被抹掉**。

**建议**：加一个 `_totalPriceManuallyEdited` 标记，用户手改过就不再自动覆盖，或在覆盖时给个轻提示。

### P1-8　文本输入没有 `maxLength`，超长即保存失败

**位置**：`tables.dart:81-97,162,168,193-198` 定义了长度上限；`vehicle_dialog.dart:186-199`、`record_dialog.dart:589-597` 等输入框没有任何 `maxLength`。

Drift 的 `checkTextLength` 会在写入时校验：

| 字段 | 上限 | 超长后果 |
|---|---|---|
| `brand` / `model` | 50 | `InvalidDataException` →「操作失败」 |
| `licensePlate` / `color` | 20 | 同上 |
| `vehicleType` | 20 | 同上 |
| `stationName` | 50 | 「操作失败」 |
| `expense.category` | 30 | 同上 |

用户复制一段长文本（比如从聊天记录里粘加油站名）就会保存失败，报错是 Drift 的英文异常，体验很差。

**修复**：输入框加 `maxLength` + `maxLengthEnforcement`，或保存前 `substring`。

### P1-9　删除车辆 / 设为默认不是原子操作

**位置**：`app_database.dart:190-196`（`deleteVehicle` 三条独立 DELETE）、`vehicles_provider.dart:150-188`（N 次 UPDATE）

`deleteVehicle` 先删记录、再删支出、再删车辆，三条语句**没有事务**。中途被杀进程 → 记录没了、车还在，用户会以为「数据莫名其妙少了一半」。（不会留孤儿行，但会丢数据。）

`setDefaultVehicle` 同理：循环里逐条 UPDATE，中断后可能出现「零个默认车」。

**修复**：两者都包进 `db.transaction(...)`。

### P1-10　长耗时导入期间 `WidgetRef` 可能已失效

**位置**：`export_provider.dart:307-380`

`importFromJson(WidgetRef ref)` 在 `await FilePicker...` 之后、事务里都用传入的 `WidgetRef` 去 `ref.read(databaseProvider)`。文件选择器可能挂起几十秒，期间用户返回上一页，`SettingsScreen` 被销毁，`WidgetRef` 失效。之后再 `ref.read` 会抛「Cannot use ref after dispose」。

概率不高（模态选择器会挡住交互），但大文件 + 用户切后台杀进程是真实场景。**建议**：Notifier 内部持有 `Ref`（`AutoDisposeNotifier` 自带），不要跨 await 使用外部 `WidgetRef`。

## 四、🟢 P2 关键优化建议（架构层面）

1. **建一层导入 DTO + 校验**
   现在的 `_importV2` 直接对 `Map<String, dynamic>` 做 `as` 强转和 `??` 兜底，校验散落且不完整。建议定义 `BackupV2` 类型 + 显式校验函数，返回 `{ok, errors[], rows[]}`，导入前先做一次「干跑」并把问题行号展示给用户。

2. **导入改成「预览 → 确认 → 提交」三段式**
   现在点「确认」后直接写库。建议先解析、统计（将导入 N 辆车 / M 条记录 / 覆盖或追加）、展示差异，再由用户点最终确认。这能同时解决 P1-3 的语义错位和「导入完才发现数据不对」。

3. **备份策略产品化**
   - 导前备份写在应用私有目录（`export_provider.dart:454-458`），Android 11+ 用户**根本看不到**，却在成功提示里给了个他打不开的路径 —— 这个「安全网」等于没有；
   - 每次导入都会新生成一份，永不清理，长期占用存储；
   - 建议：只保留最近 1～3 份、可一键导出到 SAF、在设置页提供「恢复导前备份」。

4. **统一写操作语义**
   `updateVehicle` 用 `replace`、`updateEnergyRecord`/`updateExpense` 用 `write`，两套语义混用已经直接导致 P0-2。建议全库统一为 `update(...).write(companion)`，并在代码规范里**禁掉 `replace`**。

5. **迁移备份的版本常量已过期**
   `migration_backup.dart:19` 的 `kCurrentSchemaVersion = 4`，而 `AppDatabase.schemaVersion = 5`。也就是说 **v4 → v5 升级不会产生备份**。v5 只是加一列，风险低，但常量与实际版本脱节迟早出事。建议直接从 `AppDatabase` 导出该常量，避免两处维护。

6. **错误兜底**
   `dashboard_provider.dart:179-181` 和 `:256-258` 把异常包成 `Exception('加载仪表盘数据失败: $e\n$stack')` 再抛，堆栈字符串直接进 UI。建议：release 包只显示友好文案，堆栈写本地日志文件（本地即可，不必上报），并提供「导出诊断日志」入口。

7. **测试覆盖结构性缺口**
   - 没有任何 `expenses` 增删改测试（P0-1 就是这样漏出去的）；
   - 没有导入/导出往返测试（README 自己承认了）；
   - `widget_test.dart:10-20` 只验证标题存在，**没有走 `main()`、没有打开数据库、没有触发迁移**，所谓「应用启动测试」名不副实。
   建议补三条最小回归：`addExpense` 成功落库、`setDefaultVehicle` 后 `energyType` 不变、编辑记录后 `discount` 不变。

8. **依赖治理**
   去掉 `dependency_overrides`（至少 Android 构建不要用），`ohos/` 单独分支维护。同时把阿里云 Maven 镜像与 `storage.flutter-io.cn` 写进 README 的可复现构建说明——海外贡献者构建会失败。

9. **iOS 若真要上架**
   当前 `ios/` 目录没有 `PrivacyInfo.xcprivacy`。使用 `shared_preferences`（UserDefaults）、`path_provider`、`file_picker`（文件时间戳）都需要声明 Required Reason API，否则 App Store 审核会退回。要么补齐隐私清单并在真机验证，要么在 README/商店页明确「仅 Android」。

## 残留问题 1（必须修）：`currency` 仍未 clamp

```dart

final currency = AppCurrency.values[currencyIndex];   // settings_provider.dart:152
```

而 `_restoreSettings` 依旧原样写入（`export_provider.dart:650`）：
