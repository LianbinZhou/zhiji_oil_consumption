> 时间：2026-10-25

## 一、为什么要改

原项目是作者的第一个 Flutter 项目，功能简单（车辆 + 加油记录 + 统计 + 导出）。这次重构源于四个判断：

| 问题 | 结论 |
|---|---|
| 打包体积 58.4 MB，像"很重的 App" | 实际是打了 3 个 CPU 架构，且用 debug 签名（从没打过正式包） |
| 油耗算得准不准说不清 | 算法有两个真 bug：漏算未加满的油、平均用的是算术平均 |
| 数据只有本地一份，丢了就没了 | 导入无事务、不还原默认车、备份文件落在用户找不到的私有目录 |
| 想加的功能越来越多 | 定了三条原则（免费 / 数据本地 / 不登录），砍掉广告、会员、社交、云备份、账号 |

**产品定位最终定为**：面向中国用户的纯本地 Android 记账工具，零权限、无网络、无广告。

## 二、改了什么（按模块）

### 1. 数据库 v3 → v4（风险最高）

| 旧 | 新 |
|---|---|
| 表 `fuel_records` | 表 `energy_records`（能存油也能存电） |
| `fuel_amount` / `total_price` / `price_per_liter` / `is_full_tank` | `quantity` / `amount` / `unit_price` / `is_full` |
| — | 新增 `energy_type`（gasoline/electric）、`charge_method` |
| — | 新增 `expenses` 表（保养 + 费用，用 `kind` 区分） |
| `vehicles` | 新增 `energy_type`（油车/纯电/混动） |

**迁移写法**：11 步逐列操作，每步先检查现状再执行（**幂等**，中途失败可重跑）。
**关键修复**：原来 `onUpgrade` 里有 3 处 `catch (_) {}`，迁移失败会静默跳过，下次读库才崩。现已全部删除，失败即抛出。

### 2. 能耗算法（两个真 bug）

```dart
// 旧：只取本条记录的油量 → 中途没加满的那次油被丢弃，但里程照算 → 油耗被低估
return (fuelAmount / distance) * 100;

// 新：锚点区间内所有油量求和 → 不漏算
// 平均：总能耗 ÷ 总里程（旧的是各段比值的算术平均，短途权重大，结果偏大）
```

同时统一了三处算法（统计页 / 列表页 / Excel），原来各写一套。

### 3. 导入导出重做

| 问题 | 修法 |
|---|---|
| 导入无事务 | 整体包 `transaction`，一条失败全部回滚 |
| 不还原默认车 | 导出/导入补齐 `is_default`、`settings` |
| 备份文件用户找不到（`Android/data/...` 私有目录） | 改用系统文件保存对话框（SAF），零权限 |
| 只认一种格式 | 支持 V1（历史备份，嵌套 `records`）与 V2（顶层 `energy_records`），键名映射表在规格 §8.2 |
| 重复导入翻倍 | 保留"追加"语义，但导入前自动写一份"导前备份" |

### 4. 新增功能

- **充电 / 混动**：车辆分油车/纯电/混动；纯电录入界面自动切换成充电字段；混动可切换
- **保养记录**：项目多选 + **自定义项目**（存 SharedPreferences，跨记录保留）
- **费用账本**：保险/停车/洗车/罚款等
- **统计总览（跨车辆）**：全部花费构成、年度同比、车辆对比排行、月度里程

### 5. 修复的界面 bug

| bug | 原因 |
|---|---|
| 充电记录仍显示 `L` | 记录模型没有 `energyType` 字段，无法区分 |
| "添加加油记录" | 统一改为"添加能源记录" |
| 单价用美元图标 `$` | 换成 `Icons.currency_yen`（¥） |
| 车辆页无返回箭头 | AppBar 缺 `leading` |
| 统计页底栏点不动 | 用页面内 Navigator push，只盖住内容区；改 `rootNavigator: true` |
| 叉号删不掉自定义项目 | `FilterChip` 吞掉 label 内的点击；改用 `InputChip.onDeleted` |
| 表单标签压在边框上、日期两字被裁 | 标签移出输入框（外部 `LabeledField`） |
| 日期选择器全英文 | 没配 `flutter_localizations` |

## 三、关键设计决策（审代码时容易觉得"为什么这么写"）

| 决策 | 理由 |
|---|---|
| 保养和费用**合一张表**，用 `kind` 区分 | 两者结构几乎一样（日期+类型+金额+备注），分两张等于写两遍 CRUD |
| `energy_records.energy_type` 是**记录的事实属性**，不从车辆推导 | 用户把"油车"改成"混动"时，历史记录的油耗数字不能凭空变化 |
| **里程** = 每辆车 `max(odometer) − min(odometer)` | 只统计用户实际录入的里程；表显里程不参与任何统计（各车表显不能相加） |
| 单位**固定公制**，不提供切换 | 面向中国用户，多一套单位只多一堆 bug 面 |
| 自定义费用类型**不做** | 预设清单够用，加管理页面增加复杂度 |
| 净电车的"电耗"偏高 | 按充电桩计费电量算，实际进电池有损耗（约 10%），已在界面注明 |

## 六、审核时可以质疑的三个点（我自己也不完全确定）

1. **`expenses` 表的 `kind` 判别列**：现在用 `maintenance`/`other` 两个值，`category` 存细分类型。如果以后要加"收入"或"年检提醒"，这套结构还撑得住吗？
2. **迁移的幂等实现**：靠 `PRAGMA table_info` 检查列是否存在。SQLite 的 `ALTER TABLE RENAME COLUMN` 在不同版本上行为是否一致，没实测所有版本。
3. **`--split-per-abi` 后的 versionCode**：arm64 是 2003，armv7 是 1003，universal 是 3。以后如果改发 universal 包，版本号会倒退，系统可能拒绝升级。
