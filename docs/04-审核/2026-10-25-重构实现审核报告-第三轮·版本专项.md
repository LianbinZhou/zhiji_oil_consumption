## 二、版本专项（本轮重点）

### 2.1 实测：包里到底是什么版本

```

$ apksigner verify --print-certs dist/zhiji_oil_arm64_v1.0.0.apk
```

结论：**签名是自签 release 证书（不是 Android Debug 证书）** ✅；`pubspec 1.0.0+3` 与 arm64 的 `2003` 完全对应（AGP 的 ABI split 规则：`base×1000 + abi 偏移`，v7a=1、arm64=2、x86=3、x86_64=4），说明版本号链路本身是通的。

### 2.2 [MA2] `versionCode` 降级陷阱：数字是 2003 vs 3

- **证据**：上面 badging 输出。
- **机制**：ABI split 把 `3` 变成 `2003`（arm64）。而 universal 包仍然是 `3`。
- **影响**：用户装了 `dist` 里的 arm64 包（2003），将来若发布 universal 包（3），Android 会认为这是**降级**，安装被拒（"应用未安装"/"版本低于当前版本"），用户必须先卸载——**卸载会删库，而这个 App 没有云端**，只能先导出 JSON。这是"用户丢数据的最后一道人工关卡"。
- **现状风险点**：`build/app/outputs/flutter-apk/app-release.apk`（13:28、versionCode **2**、且是**本轮修复前的旧代码**）还躺在构建目录里。任何人 `ctrl+c / ctrl+v` 把它当"通用包"发出去，就会同时造成两个问题：发出旧代码 + 埋下降级地雷。
- **建议**（低成本、一次性）：
  1. 在 `重构目标 §七` 或 README「构建」节写死一条**发版铁律**：*只发布 `--split-per-abi` 产出中的 `arm64-v8a` 包，永不发布 universal 包*；若要发通用包，必须先把 `pubspec` 的 build 号乘 1000 以上（或改用 `abiFilters` 单 ABI，让 universal 不存在）；
  2. 脚本在复制前删掉 `%APK_DIR%\app-release.apk`（或在脚本末尾提示"universal 包已作废，勿发布"）；
  3. 顺手把 `build/` 里那个 13:28 的 `app-release.apk` 删掉（`build/` 不入库，但人是会点进去的）。

## 三、Blocker

### [B1] 一键打包脚本必然失败：`flutter analyze` 的非零退出把 release 构建卡死

- **位置**：`build_apk.cmd:27-32`
- **证据**：
  ```
  build_apk.cmd:
    27: echo [2/4] flutter analyze
    28: call flutter analyze
    29: if errorlevel 1 goto failed          ← 新增的硬闸
    31: echo    (analyze OK; only errors block the build)   ← 注释与代码相反

  实测（本机，两次）：
    $ flutter analyze > /dev/null 2>&1; echo $?          → 1
    $ cmd //c "call flutter analyze >nul 2>&1 && echo OK || echo FAIL"  → FAIL
    $ flutter analyze 末尾                                → 5 issues found（全部在 app_database.g.dart）

  analysis_options.yaml → 无 analyzer.exclude（未排除生成文件）
  ```
- **原因**：`flutter analyze` 只要报告任何 issue（含 warning/info）就返回 1；项目已决定"生成文件的 5 条警告排除在外"，但**没有在配置层面排除**，于是检查结果是 1，硬闸直接 `goto failed`。
- **影响**：
  - `7.3 一键脚本`这条验收**现在不可能通过**（脚本停在 `[2/4]`，永远到不了构建与复制）；
  - `dist/zhiji_oil_arm64_v1.0.0.apk`（19:52）不可能是这个脚本产出的——**推测**是手工跑 `flutter build apk --release --split-per-abi` 后再手工复制（验证方法：双击 `build_apk.cmd`，看它是否停在 `[2/4]` 并打印 BUILD FAILED）；
  - 更隐蔽的风险：以后有人"为了让它跑通"把日志里的失败当成噪音而删掉硬闸，就退回到"分析器根本不挡事"的老状态。
- **建议**（三选一，任选其一即可让脚本恢复）：
  1. **首选**：在 `analysis_options.yaml` 加
     ```yaml
     analyzer:
       exclude:
         - "**/*.g.dart"
     ```
     这样 `flutter analyze` 报 0 issues（与项目"手写 0 警告"的结论一致），脚本原样可用；
  2. 或脚本改成 `call flutter analyze --no-fatal-warnings --no-fatal-infos`；
  3. 或在脚本里保留硬闸但改为"只对 error 失败"：捕获输出并 `findstr " error "` 判断。
- **附带**：脚本步骤编号现在是 `[1/4] [2/4] [2.5/4] [3/4] [4/4]`，建议统一成 `/5`（Nit）。
