### [B1] 三份核心文档对功能范围给出三个不同答案

- **位置**：`docs/02-重构/2026-10-25-重构目标与验收标准.md`（第四节"明确不做"）与 `docs/02-重构/2026-10-25-产品原则与功能边界.md`（六、七节）与 `docs/02-重构/2026-10-25-功能规格说明.md`（第一节）三者互斥。
- **证据**：

  重构目标 §四：加新功能（保养记录、多车对比、加油提醒）→ 不做
  产品原则 §六：扩展档位 → 已定：档位 B（用车账本）  ← 保养 + 费用就是要加

  ```
- **原因**：三份文档写于同一天的不同讨论阶段（原则/规格显然晚于目标文档），但没有回写《重构目标与验收标准》。它至今仍是唯一带"五项清单 + 工作量 + 验收表"的施工文档，却顶着"不加新功能"的封条。
- **影响**：施工者按《重构目标》干活，就会得出"本次不写 expenses 表、不做充电"的结论，与另外两份文档整体冲突；如果反过来按规格做，那 2.5 天的工作量估算和五项清单又全部失效（实际至少翻倍）。
- **建议**：给《重构目标与验收标准》出第二版，二选一：
  - 方案 A（推荐，符合已拍板的档位 B）：把第 6 项"数据模型 v4 + 保养 + 费用"补进清单，工作量重估；同时删掉 §四 里的"保养记录"。
  - 方案 B：明确"档位 B 属于重构之后的下一个版本"，把《功能规格》和《产品原则》的这一段标为"V2 设计，未实施"，本次只做五项清单。

### [B2] 《功能规格》的导出格式与"旧备份"结构都与代码实测不符

- **位置**：`docs/02-重构/2026-10-25-功能规格说明.md` 第六节；实测代码 `lib/features/export/providers/export_provider.dart:70`、`:77-110`、`:304`、`:339`。
- **证据**：
  ```
  export_provider.dart:70   'version': '1.0',          // 字符串，不是数字 2
  export_provider.dart:77   vehicleData = {... 'records': <dynamic>[]}   // 记录挂在车辆下
  export_provider.dart:95   vehicleData['records'].add({...})            // 嵌套结构
  export_provider.dart:304  if (!jsonData.containsKey('version') || !jsonData.containsKey('vehicles'))
  ```
  规格第六节写的是 `"version": 2`，顶层平铺 `vehicles` / `energy_records` / `expenses`；
  "向后兼容"要求写的是"旧备份里字段名是 `fuel_records` 且没有 `energyType`" ——
  但真实旧备份里既没有顶层 `fuel_records`，版本号也是字符串 `'1.0'`。
- **原因**：规格是按"理想的两张表模型"写的，没有回头读 `export_provider.dart` 的实际产物。
- **影响**：按规格实现导入，`jsonData['fuel_records']` 拿到的是 `null`；更糟的是，如果照规格写"缺 `expenses` 按空处理"却不处理嵌套结构，**用户多年的真实备份会导入成 0 条记录且提示成功**。这是唯一的数据保险，风险等级最高。
- **建议**：规格改成分版本描述：
  - V1（真实存在）：`{version:'1.0', exportTime, vehicles:[{... , records:[...]}]}`，无 `isDefault`；
  - V2（本次新增）：平铺 `energy_records`/`expenses` + `schemaVersion` 数字；
  - 导入器按 `version` 分派，V1 走"嵌套解包 + 按车辆能源类型补 `energyType`"。
  - 先写一份"导入兼容性矩阵"（V1 有/缺哪些键 → 怎么补），再动手。

### [B3] 导入路径没有事务、没有幂等、不还原默认车——"数据可恢复"这条标准目前站不住

- **位置**：`export_provider.dart:262-360`（`importFromJson`）；导出侧 `:77-95`。
- **证据**：
  ```
  导出车辆字段清单（:77-86）：id/brand/model/licensePlate/color/vehicleType/notes/createdAt/updatedAt
                              ← 没有 isDefault（tables.dart:41 有这个字段）
  导入（:323-357）：逐条 insertVehicle / insertFuelRecord，无 transaction，无 DELETE，
                    无重复检测，返回值直接 "导入成功"
  ```
- **原因**：导入写成了"循环插入"，把"追加"当默认语义，但界面没有"这会重建一份数据"的提示，也没有先清空/先备份。
- **影响**（三种都会真实发生）：
  1. 用户点两次导入 → 数据翻倍，且因为 id 重排、里程重复，油耗统计算出来的结果会乱；
  2. 第 800 条记录抛异常 → 前 799 条已落库，App 显示"导入失败"，但数据已经脏了，用户还得手工删；
  3. 换手机恢复后"默认车"丢失（`vehicles_screen.dart:161-181` 的默认徽章不再出现）。
- **建议**（最小集，成本极低）：
  - 导入整体包 `transaction {}`；
  - 导入前先自动 `exportToJson()` 一份"导前备份"到同目录；
  - 明确语义并在 UI 写清：**"导入 = 追加到现有数据"** 或 **"导入 = 覆盖（先清空）"**，二选一并落进规格；
  - 导出/导入补 `isDefault`（以及 `settings` 里的单位/货币/主题，若希望"完整还原"）；
  - 验收用例：同一份备份导入两次 → 记录条数不变（幂等）或明确翻倍且可撤销。

### [B4] 迁移方案不完整，且现有 `onUpgrade` 会把失败吞掉

- **位置**：`docs/02-重构/2026-10-25-功能规格说明.md` 第七节；`lib/data/database/app_database.dart:41-56`；字段改名依据 `功能规格` §3.2 与 `tables.dart`。
- **证据**：
  ```

                 CREATE TABLE expenses / vehicles ADD energyType
  规格 §3.2 同时把 fuelAmount→quantity、totalPrice→amount、pricePerLiter→unitPrice、
            isFullTank→isFull 全部改名
  现有实现：
  app_database.dart:45   } catch (_) {}
  app_database.dart:48   } catch (_) {}
  app_database.dart:51   } catch (_) {}
  app_database.dart:52-55 if (from < 3) { // v3: schema alignment, no new columns added }

- **原因**：表结构描述（§3.2）和迁移步骤（§7）不是同一份清单产出的；`try/catch(_)` 是"让编译过"的临时手段被留在了生产代码里。
- **影响**：
  1. 照 §7 五步实现、同时按 §3.2 的新列名写 Drift 表定义 → Drift 生成的 SQL 会去查 `quantity` 列，而库里的列还叫 `fuelAmount`，**老用户一升级就 `no such column`**；

  - 迁移前把 `zhiji_oil.db` 复制成 `zhiji_oil.db.pre-v4.bak`（Drift 有 `beforeOpen`/`onUpgrade` 时机可做）；
  - 删掉所有空 `catch`，改成"记录日志 + 弹一次可读的失败提示"，并保留可回滚的备份文件；
  - 迁移做成**表驱动的集成测试**（见 M6/ Minor m4）。

### [M1] "锚点区间内的油量"没有定义，现有实现会漏掉中间未加满的加油量

- **位置**：`statistics_provider.dart:100-111`、`dashboard_provider.dart:127-143`、`fuel_record.dart:87-93`；规格 `§5.1`；重构目标 `1.2` 与其测试用例。
- **证据**：
  ```
  statistics_provider.dart:100  final fullTankRecords = sortedRecords.where((r) => r.isFullTank).toList();
  statistics_provider.dart:105  consumption = fullTankRecords[i].calculateFuelConsumption(fullTankRecords[i-1].odometer);
  fuel_record.dart:92           return (fuelAmount / distance) * 100;   // 只取"本次这一条"的油量
  ```
  规格 §5.1 的措辞是"相邻两次加满之间的加油量"（语义正确）；
  重构目标 §3 第 5 项用例写的是"两次加满，里程差 500 km、加油 35 L → 7.0 L/100km"（按单条）。
- **原因**：公式把"一次加油"当成了"一个区间的全部耗油"，只在"每次加油都加满"时才成立。
- **影响**：用户中途有一次没加满（很常见：只加 200 元），那次的油量被完全丢弃，而里程差照算 → 油耗被**低估**，且低估多少取决于漏了几笔。亮灯法同理（亮灯间隔里往往夹着若干次加油，必须求和）。混动/电车的"两次充满之间的电量"更是必然多笔。
- **建议**：规格里把算法写成显式的两行公式，并加一条 UI 提示：
  ```dart
  // 锚点 a → b（同能源类型）
  fuel = sum(quantity of records in (a, b]  where energyType 相同)   // 含未加满/未充满
  consumption = fuel / (b.odometer - a.odometer) * 100
  ```
  测试用例同步改成"加满 → 未加满 20 L → 加满 15 L，里程差 500 km → (20+15)/500*100 = 7.0"。

### [M2] 平均油耗用的是"各段油耗的算术平均"，不是加权平均

- **位置**：`statistics_provider.dart:99-111`、`:169-183`、`dashboard_provider.dart:127-143`。
- **证据**：`averageFuelConsumption = totalConsumption / count;`（每段 L/100km 各占 1 票）。
- **原因**：把"每段一个比值"直接平均，等价于假设每段里程相同（`H_total` 应除以总里程）。
- **影响**：一段 50 km 的短途和一段 900 km 的长途权重相同 → 短途（通常油耗高）把结果拉高；同一台车，统计页的"平均油耗"和"总加油量 ÷ 总里程"会给出两个数，用户一算就觉得 App 不准。
- **建议**：口径统一成 `总油量 / 总里程 × 100`（与"每公里成本 = 总花费 / 总里程"同构），并在规格 §5.1 写死一句话；若要保留分段平均，得注明"各段等权"。

### [M3] Excel 导出的"油耗"列与统计页不是同一套算法

- **位置**：`export_provider.dart:207-221`。
- **证据**：
  ```
  215  String fuelConsumption = '-';
  218  final consumption = record.calculateFuelConsumption(previousRecord.odometer);
  ```
  这里 `records` 是**全部记录**（未过滤 `isFullTank`、未看 `isLightOn`），相邻即配对。
- **影响**：同一个 App，统计页与导出表格对"这次油耗"给出两个不同数字（统计页要 `isFullTank`，导出不要），用户拿 Excel 去对比必然质疑数据可信度。
- **建议**：Excel 里要么复用同一个 `ConsumptionCalculator`（单一实现），要么把这列改名为"本次里程油耗（不分加满状态）"并在表头/说明里讲清；同时补上"算法"列（加满法/亮灯法）。

### [M4] 单位切换的目标单位没有定义，第 1.1 项现在无法验收

- **位置**：重构目标 `1.1` 验收条目；`settings_provider.dart:11`、`:21`（只有 `miles('英里','mi')`、`gallons('加仑','gal')`）。
- **证据**：`settings_provider.dart` 只存了枚举，没有任何换算函数（全项目 `distanceUnit`/`fuelUnit` 引用都在 `settings_screen.dart`，与摸底文档一致）。
- **影响**：`L/100km` 换成 `gal/100mi`（越小越省）还是 `MPG`（越大越省）？两者数值方向相反。验收条件只写"油耗单位跟着变"，实现者随手选一个就能"通过验收"，但用户看到 `MPG` 数字变小会以为车变费油。同理：
  - 纯电 `kWh/100km` 在英里制下应是 `kWh/100mi`（还是保留 100km？）；
  - 混动的"每公里成本 ¥0.42"要不要变成"每英里成本"；
  - 录入界面输入框的标签（"加油量(升)"）要不要跟着变，还是"输入永远用公制、显示才换算"。
- **建议**：规格加一张换算定义表（源单位 → 目标单位 → 公式 → 保留位数 → 显示标签），并明确"**存储永远公制，只在展示层换算**"（否则往返换算会累积误差、也让导出/导入变得不可逆）。

### [M5] 备份文件到底落在哪里没定，而"零权限"约束限制了可选方案

- **位置**：`export_provider.dart:122-126`、`:243-247`；原则文档第四节（零权限）、功能规格 §8。
- **证据**：
  ```
  122  var directory = await getDownloadsDirectory();
  123  directory ??= await getApplicationDocumentsDirectory();
  260  message: 'Excel已保存到: $fileName',
  ```
- **原因**：`path_provider` 在 Android 上给的是**应用私有**目录，不是用户能在"文件管理 → 下载"里看到的位置。
- **影响**：用户看到"备份已保存到 zhiji_oil_backup_xxx.json"，去文件管理器找不到 → 换机时拿不到备份 → 而这个 App **没有云端，备份是唯一的数据保险**。文件选择器 `file_picker` 的保存/分享能力也决定了是否需要额外权限。
- **建议**：规格里明确三选一并写进验收：
  1. `file_picker.saveFile`（SAF，用户自选目录，零权限，推荐）；
  2. 存私有目录 + `share_plus` 分享出去（零权限，但多一个依赖）；
  3. 存私有目录并在设置页显示完整路径 + "打开目录"入口（零权限，体验最差）。
  同时把"导出成功后弹窗给出可点击的路径/分享按钮"写进验收（现状只给文件名）。

### [M6] 表结构一变，连带受影响的地方没有逐条列出

- **位置**：功能规格 §3、§5；受影响代码 `app_database.dart:234-273`。
- **证据**：`getTotalCost` / `getTotalFuel` / `getMaxSingleCost` / `getMinPricePerLiter` / `getMaxPricePerLiter` 全部直接 `selectOnly(fuelRecords)` 聚合。
- **影响**：`fuel_records → energy_records` 一改，这 5 个 SQL 聚合全部要重写（且"总油量"要按 `energyType` 过滤，"平均油价"在电车/混动上没有意义）。另外两处规格空白：
  - "每公里成本 = 总花费 ÷ 总里程"里的**总里程**没定义（应为 `max(odometer) - min(odometer)`，并注明不含首条记录之前的里程）；
  - 混动车的"油耗/电耗"要按 `energyType` 分组配对锚点，若某车既有加油又有充电记录、锚点混用，必须强制"同能源之间配对"，否则里程差会被两套能源共同消耗 → 两个指标同时错。
- **建议**：规格加一节"重构影响面清单"（表/查询/Provider/页面/导出/测试各一行），把这些点列成勾选表；每改一处数据库方法配一条集成测试。

### [M7] 车辆换能源类型后，历史记录怎么算没定

- **位置**：功能规格 §3.1、§7（只写"回填一次 `energyType`"）。
- **影响**：用户把"汽油"改成"混动"（或补录第二辆车），历史记录的 `energyType` 仍是 `gasoline`。此时"油耗"能算、"电耗"永远为空——统计页该显示什么？如果反过来按车辆类型推断，那 `energyType` 字段的存在意义又没了。这是**数据契约**问题，写不清楚后面每处都要打补丁。
- **建议**：规格明写"`energy_records.energyType` 是记录的**事实属性**，录入时按当时的车辆类型写入，车辆类型变更**不回改**历史记录"，并给出统计页在"混动车无充电记录"时的降级显示规则。
